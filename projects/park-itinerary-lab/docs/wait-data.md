# 待ち時間データの運用

## データの流れ

1. Queue-Timesの公開APIからランドとシーの現在値を取得します。
2. 施設IDを `web/data/queue-times-map.json` で対応付けます。
3. 最新値をデータ専用ブランチ `park-wait-data` の `live-waits.json` に保存します。
4. 稼働中で更新から15分以内の記録を `observations.json` に蓄積します。
5. 毎晩21:55を目安に、保存済みの全ての月別記録と現在のアクセス権で取得できる履歴を合わせて、終了した営業日までの分で再学習し、`wait-model.json` を更新します。学習最終日より後の訪問日にだけ使います。
6. アプリ起動時に最新の公式カタログ・祝日・共通モデルを確認します。当日の組み替えと「最新の待ち時間を取得」ではThemeParks.wikiの公開Live REST APIで現在の待ち時間・稼働状態を確認します。接続できなければ収集済みのQueue-Timesの記録を使い、その取得時刻を表示します。古い記録をリアルタイム値として使いません。

収集はGitHub Actionsの **Collect park waits and train predictions** で動かします。毎日8時台〜21時台（日本時間）の15分間隔です。実行の遅延があり得るため、画面では施設ごとの更新時刻も確認します。21:55の実行が抜けても、次の収集で直近の終了営業日までをまとめて処理します。失敗した場合は前のモデルを保持し、同じ営業日の自動再試行は6時間以上空けます。実行状況はデータブランチの `training-state.json` に記録します。データの更新でPages全体を再ビルドしません。

初回はActionsから **Run workflow** を実行できます。定期実行も既定ブランチのワークフローで始まります。収集先のブランチがない場合は初回に作ります。GitHub Actionsの書込権限はこのデータブランチへのコミットに使います。

## 日付を指定して予測の精度を確かめる

[予測精度レポート](https://shogo-ishikawa.github.io/2026_3Q_M4Th4/park-itinerary-lab/accuracy.html) でランドまたはシーと日付を選びます。対象は、個人の希望や手入力の待ち時間を含まない共通の予測です。営業中は終了した時間枠までの途中結果を表示します。

毎晩の更新で、翌日の混雑の見込みと各施設の30分枠ごとの待ち時間を `forecasts/YYYY-MM-DD.json` に保存します。前夜に作れなかった場合は当日最初に作成できた時点で、これから始まる枠だけを記録します。作成後はその日の予測を固定します。予測の保存が始まる前の日付は採点できません。

営業中の照合にはQueue-Timesでその後に掲示された通常列の待ち時間を使います。施設ごとに同じ30分枠の掲示値の中央値を求め、1施設の1枠を1件として数えます。たとえば予測40分に対して掲示値が25分なら、その枠は15分の過大予測です。平均絶対誤差はずれの大きさ、符号付きの平均誤差は長め・短めのどちらに偏ったかを示します。照合できた割合の分母は終了済みの予測枠です。欠測や休止を待ち時間0分として扱いません。

閉園後は同じ事前予測をThemeParks.wikiの施設別履歴とも照合します。30分枠ごとに最後に更新された通常列の掲示値を使い、更新を確認できた枠だけを数えます。元の履歴は配布せず、パーク別の件数と誤差などの集計を `accuracy-history/YYYY-MM-DD.json` に保存します。2つの情報源では集計方法と観測時間が異なり、同じ枠も含み得るため、件数は別々に表示します。

園全体の混雑は、事前に固定した通常の待ち時間と当日の掲示値から判定します。同じ施設の同じ時間帯を比べ、2つ以上の時間帯を照合できる施設が3つ以上、全体で異なる時間帯が3つ以上そろった時に3段階の判定を出します。入園者数や園路の人口密度は測定していません。学習時に過去の日付を取り分けた検証成績は、日々のレポートとは別にモデルに記録されます。

## 記録と学習

開園から90分は10分、それ以降は30分につき1施設1件を残します。最近の記録は最大60日・10万件です。月別の記録は収集開始から全期間を保持し、24か月を過ぎても自動で削除しません。サーバーの再学習では適格な全記録を使います。ブラウザ内の再学習は処理負荷を抑えるため最大5万件を期間全体から均等に選び、利用可能件数と使用件数をモデルに記録します。休止中の0分は待ち時間の観測として学習しません。天気が取得できない場合は不明のまま保存します。

`web/wait-model.js` が学習の正本です。正則化した線形回帰（リッジ回帰）をブラウザと定期更新の両方から使います。特徴は施設、時刻の周期と開園後の経過時間、曜日、季節、祝日前後、時間別天気・気温・降水量、個別イベントです。施設別の時間帯の差も学習します。待ち時間を施設の基準値で割った値を学び、結果を分へ戻します。7日以上・100件以上になるまで学習済みとは表示しません。

最後の約20%の日付（最低2日）を検証用に取り分けます。残りの日付だけで学習して検証日の待ち時間を予測し、平均絶対誤差（MAE、分）を求めます。傾向モデルのMAE以下だった場合だけ学習モデルを採用します。その後、全記録で係数を学び直します。学習に使った最終日より後の訪問日にだけ使うため、過去日の検証へ未来の記録が入りません。

v1.3.0は2026年11月11〜17日の許可された履歴を使った初期モデルを同梱します。ランド2,798件・シー2,663件で学び、16〜17日を検証用にしました。17日は取得時点までの記録です。このモデルの利用対象は11月18日以降です。学習最終日と同じ日や前の日には使いません。

直近7日だけでは季節の違いや祝日の効果を十分に比較できません。条件別の件数と日数を表示し、平均は5件・2日以上、相関係数は20件・3日以上から表示します。比較する条件がそろわない欄は記録不足として扱います。相関は記録内の傾向であり、天気やイベントだけが待ち時間を変えたことを示すものではありません。

新しいモデルが未学習になったり有効な日数が減ったりした場合は、前の検証済みモデルを保持します。同じ7日分でも日付が新しくなった履歴は更新対象です。サーバーは全記録、ブラウザは全期間から均等に選んだ記録を使うため、古い季節を単に直近の日付で押し出しません。

## パーク全体の混雑の想定

「比較的すいている・ふつう・混み合う」の目安は、施設ごとの待ち列の長さから推定します。人気施設ばかりで予測値が高く見えることを避けるため、同じ施設の同じ時間帯と比較します。10・12・14・16・18時台に分け、各施設で比較できる時間帯の予測値合計を過去平均の合計で割ります。3施設以上の比の中央値を使い、0.85倍以下を「比較的すいている」、1.15倍以上を「混み合う」、その間を「ふつう」の目安とします。これらの境界はしおり作成用の設定です。表示は入園者数や通路の人口密度の測定値ではありません。検証を通過したモデルがあり、比較できる施設・時間帯・日数がそろった場合に学習値を使います。それ以外は暦からの目安を表示します。個別施設のモデル予測と新しい現地待ち時間には、ここで求めた混雑の倍率をもう一度掛けることはありません。

学習用の1件は「ランド／シーのどの施設で、いつ、何分と掲示されていたか」です。実際に並んでから乗車するまでの時間を測った記録とは区別します。稼働状態、観測時刻、情報源も保存し、休止・欠測を0分として数えません。両園の同じ日を時間帯別に集め続けると、平日と週末のほか雨の日やイベント期間も比べられます。精度を評価するときは過去の日付で学習し、その後の複数日に対して単純な傾向予測と誤差を比べます。個々の施設や早朝・夕方も別々に確認すると、全体平均だけでは分からない偏りが見つかります。

## 公式情報の日次更新

公式情報の日次更新は毎朝6:15 JSTにクラウド実行します。公開リポジトリの最新の `scripts/refresh_official_bundle.py` を使い、確認した結果だけを `park-wait-data` へ保存します。GitHub-hosted runner はLinux・macOSの両方で公式サイトへの通信がタイムアウトしたため、日次取得の実行元を分けています。GitHub Actionsの **Update official park catalogue** は手動確認用です。公式の施設一覧・運営カレンダー・休止情報・イベントページ・店舗メニュー・内閣府の祝日CSVを確認します。結果は同じデータブランチの `catalogue.json` と `calendar.json` に保存します。通信に失敗した情報は前回確認済みの内容を保持します。初回は同梱データを使います。取得成功日時と更新試行日時は分けて記録し、取得できなかったことを画面と差分レポートに表示します。メニューと祝日カレンダーの更新は個別に試行します。

施設の `dailySchedules` が日付別の営業時間と公演回、`closedPeriods` が明示された休止期間です。営業時間が「ー」で未発表の欄は休止と判定しません。未登録施設やDPA対象の変更はレポートに残し、位置・通路・料金を確認してからカタログへ加えます。公式の情報と計画用の概算を区別します。追加した店舗の位置と短い接続距離は概略地図のエリアをもとにした目安です。予算は注文内容に合わせて変更できます。

定期タスク「Park公式情報更新」を登録したCodexチャットをアーカイブすると、紐づいたタスクは削除されます。公式情報の自動更新を継続する場合はそのチャットを残すか、先に公式サイトへ接続できる別の実行環境へ日次処理を移します。待ち時間・天気・学習のGitHub Actionsは独立して動きます。GitHubの定期実行には遅延や欠測があり、公開リポジトリが60日間無活動の場合は停止します。[Codexのアーカイブ](https://help.openai.com/en/articles/20001333-archiving-and-deleting-codex-chats-in-the-chatgpt-app) ／ [GitHubの定期実行](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 過去履歴から初期学習・再学習

[ThemeParks.wiki](https://www.themeparks.wiki/)の履歴取得期間はアクセス権によって変わります。匿名は直近7日、無料キーは30日です。対応する契約済みキーがあれば400日または全アーカイブを読み込めます。東京の両パークの公開カバレッジは2021年7月4日からですが、その全期間を匿名で取得できるわけではありません。コードは `/me` が返す実際の権限と残りリクエスト数、パークごとのカバレッジを照合します。範囲外を要求したり制限を回避したりしません。利用条件で認められた予測モデルの作成に使い、公開するのは係数・検証結果・十分な件数の集計です。元の履歴を公開用ブランチやZIPへ含めません。毎晩の処理は一時フォルダに取得して学習し、処理後に削除します。キーがない現在の初期モデルは7日分です。長期データを取得していない段階で季節やイベントの効果を確かめたとは表示しません。

```sh
python3 scripts/bootstrap_wait_history.py --catalogue web/data/parks.json --calendar web/data/calendar.json --output-model outputs/wait-model.json --private-dir /絶対パスのリポジトリ外フォルダ
```

### 取得可能な過去期間を広げる

[ThemeParks.wikiのFreeプラン](https://www.themeparks.wiki/pricing)から無料キーを発行できます。パーク全体の履歴は1園1日が1リクエストです。両園30日分で最大60回が目安で、無料キーの履歴枠は毎時600回です。実際の収録期間や欠測により利用できる日数は変わります。

無料キーを持っている場合は環境変数 `THEMEPARKS_API_KEY` に設定します。GitHub Actionsではリポジトリの **Settings → Secrets and variables → Actions → New repository secret** から同名のシークレットとして保存します。手動ですぐに試す場合は **Actions → Collect park waits and train predictions → Run workflow** を使います。キーをブラウザの設定欄やソースファイルへ入れる必要はありません。設定後の自動実行は30日など実際に許可された期間を対象にします。

長期のバックフィルはリポジトリ外の同じフォルダを繰り返し指定します。取得済みの日付を再利用し、最新数日だけを再確認します。一回の処理は指定した上限とAPIの残り予算で打ち切り、未取得のパーク別日数をモデルの `bootstrap.historyRequestsPending` に記録します。次の実行は欠けている古い日付から続きを取得します。

```sh
python3 scripts/bootstrap_wait_history.py --catalogue web/data/parks.json --calendar web/data/calendar.json --history-dir /保存済みの月別履歴 --output-model outputs/wait-model.json --private-dir /リポジトリ外の専用フォルダ --max-history-requests 1000
```

`--days` を省略すると権限で許可された全期間が対象です。`--start-date` や `--days` を指定しても権限と実在するデータの範囲を超えません。公開リポジトリのActions cacheや配布ZIPへ、この専用フォルダを保存しないでください。公開するのは出力した派生モデルです。

365日分の施設別待ち時間をさかのぼる場合、両園で最大730回のパーク別・日別履歴取得が目安です。十分な取得権限のあるキーを環境変数に設定し、上のコマンドに `--days 365` を追加します。長期履歴を後から再学習にも使う場合は、取得先の非公開フォルダを保持します。公開リポジトリにあるのは配布用モデルと集計結果です。観測のない日があれば学習日数は365日を下回ります。[アクセスプラン](https://www.themeparks.wiki/pricing) ／ [東京の両園を含む収録範囲](https://www.themeparks.wiki/coverage)

### 手元の過去記録を合わせる

利用できるCSVやJSONがある場合は次の手順で全期間を取り込めます。複数の `--input` を指定でき、重複する施設・日付・時間帯は整理します。時刻、待ち時間、天気、気温、降水量、イベントID、観測元を保持します。

```sh
python3 scripts/import_wait_history.py --input /記録/過去の待ち時間.csv --input /記録/別の年.json --output-dir outputs/imported-waits --enrich-weather
python3 scripts/train_wait_model.py --observations outputs/imported-waits/observations.json --history-dir /保存済みの月別履歴 --calendar web/data/calendar.json --output outputs/wait-model.json
```

過去イベントの期間が分かる一覧やCSVの `event` 列を使います。現在のイベントを過去の全日付へ当てはめることはありません。過去のイベント記録がない期間は、イベント別の効果の評価には使える情報が限られます。`--enrich-weather` はOpen-Meteoの時間別再解析を時刻で結合し、既存の気象値は保持します。取得できない値を晴れや0mmに置き換えません。

履歴の気象条件はOpen-Meteoの過去の気象モデル予報を使用します。観測所の実測値とは区別して出典を記録します。[Powered by ThemeParks.wiki](https://www.themeparks.wiki/) ／ [利用条件](https://www.themeparks.wiki/terms) ／ [過去の気象予報](https://open-meteo.com/en/docs/historical-forecast-api)。

## アプリで使う値

| 条件 | 待ち時間 |
| --- | --- |
| 手動モード | 希望欄で指定した値 |
| 訪問日が今日で、更新から15分以内、並び始める時刻が現在から60分以内 | 公開APIからの観測値 |
| 対象日より前の記録で学んだモデルが検証で改善 | 学習モデルの予測 |
| 近い時刻の履歴がある | 曜日・天気・イベントの近い観測を重み付け |
| 対応する記録がない | 曜日・時刻・天気・期間イベントの傾向モデル |

現在停止中の施設は残りの予定から外します。再開の情報を取得するまで停止扱いを保持し、通信失敗や欠測だけでは候補へ戻しません。現在の稼働状態は今日の計画にだけ使います。乗車・体験の所要時間は待ち時間とは別です。外部データの更新で所要時間は変わりません。

## 個人の記録

現地で見た待ち時間をフォームから記録できます。天気が自動の場合は記録した時刻の予報・気温・降水量を付けます。別日の予報を当日の観測へ流用しません。CSV読み込みと合わせ、端末内で学習して計画へ使えます。JSONで保存した場合は記録とモデルも復元できます。共有リンクには履歴・モデル・取得値を入れません。個人の記録を共通の公開データへ自動送信する処理はありません。

## ローカルで実行

Python 3.12とNode.js 18以上を使います。学習処理に追加のPythonライブラリは不要です。

```sh
python3 scripts/collect_wait_data.py --output-dir outputs/waits
python3 scripts/train_wait_model.py --observations outputs/waits/observations.json --output outputs/waits/wait-model.json
```

## 出典と利用方法

- [Queue-Times API](https://queue-times.com/en-US/pages/api)：約5分ごとの現在値と稼働状況を公開しています。アプリに「Powered by Queue-Times.com」のリンクを表示します。ランドは274、シーは275です。ブラウザへのCORSヘッダーがないため、GitHub Actionsで取得してからアプリへ渡します。
- [ThemeParks.wiki](https://www.themeparks.wiki/api)：許可された直近履歴から予測モデルを作ります。利用条件に従い元の履歴を一括配布しません。画面に「Powered by ThemeParks.wiki」のリンクを表示します。
- [内閣府の祝日CSV](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)：祝日・振替休日・祝日前後の判定に使います。
- [Open-Meteo](https://open-meteo.com/en/docs)：パーク周辺の天気を取得します。[非商用・教育利用の条件](https://open-meteo.com/en/terms)と[CC BY 4.0](https://open-meteo.com/en/license)に従い、天気の表示に出典リンクを付けます。
- [気象庁](https://www.jma.go.jp/bosai/forecast/)：千葉県北西部の天気と千葉・銚子地点の気温を予報の区切りとともに表示します。提供されない降水量は補完しません。Open-Meteoと気象庁の予報を `weather-forecast.json` へ保存し、日中は約1時間、夜間は3時間ごとに更新を試みます。取得失敗時は前回の取得・発表日時を維持します。
- Yosocal、Queue-Timesの混雑カレンダー、ディズニーリアルは画面から開ける比較用リンクです。各ページの予想や過去履歴を自動収集する機能はありません。

## 公式情報の更新を手元で確認する

```sh
python3 scripts/refresh_official_bundle.py --output-dir outputs/official-update
```

Python標準ライブラリで営業予定・休止・イベント・メニュー・祝日を取得します。既存の公開カタログを読み込む場合は `--previous-catalogue /保存先/catalogue.json` を加えます。前回の `calendar.json` が同じフォルダにあれば保持用に読み込みます。出力は `catalogue.json`、`catalogue-report.json`、`calendar.json`、`calendar-report.json` です。元HTMLや画像は配布しません。このコマンドだけでは公開しません。

通信失敗は最大1回だけ再試行します。施設一覧は3並列、メニューは4並列です。同じ店舗を表す複数の売り場では一回の応答を共有します。取得試行と成功は別の日時で記録します。メニューは各施設の `menuCheckedOn` が最後の確認成功日で、全体の `foodMenuUpdate.checkedAt` は更新を試みた日時です。全件失敗を成功扱いにしません。

日次処理は最新mainのスクリプトで生成した公開JSONだけをデータ専用ブランチへ反映します。反映直前にデータブランチのHEADを確認し、他の待ち時間収集のコミットを保持します。競合した場合は最新のデータから再度結合し、強制更新しません。新施設の位置・料金・DPA変更は引き続き確認が必要です。
