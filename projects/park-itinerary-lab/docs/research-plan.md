# 研究計画：短縮利用の費用をどこに配分するか

## 1. 研究の問い

**固定時刻の予定（必須のショーなど）があると、どの施設の時間短縮に費用を配分するべきかは、どのように変わるか。**

一日の予定には、ショーの開演のように時刻が決まった予定があります。その前後の時間の使い方によって、有料の時間短縮（以下「短縮利用」）を使うべき施設や時間帯が変わる可能性があります。この問いを、架空のパークのデータと本体モデル（[model.md](model.md)）を使って調べる土台を用意しました。

## 2. 主張しないこと

- 新しい最適化問題やアルゴリズムを考案したとは主張しません。
- 「同時最適化（方法A）は、候補を先に絞る方法（方法B）以上の結果になる」こと自体は、方法Bが方法Aの選択肢を減らした問題であることから当然で、発見ではありません。
- 架空のデータと時間帯別の待ち時間表に基づく結果を、実在のパークや実際の来園者の満足度にそのまま当てはめることはできません。
- 結論や改善率を先に作らず、計算結果をそのまま示し、そこから考察します。

## 3. 比較する方法

同じデータ・同じ制約・同じ評価関数・同じ検証関数を使います（`experiment.py` は `solve_day_plan()` を呼ぶだけで、別の最適化を実装しません）。

- **方法A（同時最適化）**: 訪問先・順序・時刻・短縮利用をまとめて決めます。
- **方法B（候補を先に絞る方法）**: 先に次の規則で「短縮利用の候補の施設」を決め、候補外の施設の短縮利用（仮定枠）を禁止して、同じモデルで解きます。

方法Bの規則（`experiment.CANDIDATE_RULE`）:

1. 基準時刻（標準は入園時刻）に並び始めた場合の通常の待ち時間から、短縮利用の残る待ち時間を引いた値を「短縮できる時間」とする。
2. 施設ごとに最も安い枠（同額なら残る待ち時間が短い枠、さらにID順）の料金を使う。
3. 「短縮できる時間 ÷ 料金」の大きい順に並べる。同点は短縮できる時間の長い順、さらに施設IDの順。料金0円の枠は比が無限大として先頭。
4. 料金の合計が予算以内に収まるものを順に候補とする（入らない施設は飛ばして次を調べる）。
5. 基準時刻に通常利用できない施設や、短縮できる時間が0分以下の施設は候補にしない（計算過程の表では、理由を「基準時刻に通常利用できない」「短縮できる時間が0分以下」と分けて表示）。
6. 取得済み枠をすでに持っている施設は、新しく買う候補にしない（取得済み枠は両方の方法で使える）。

方法Bの候補集合は「購入済みの集合」ではありません。方法Aと同じく、実際に使った枠の料金だけを追加費用に数えます。取得済み枠は両方の方法で使えます。
この比較は「情報の少ない時点で、候補を先に絞る判断」が結果にどう影響するかを調べるためのものです。

## 4. 実験条件

標準の小さなデモ（02 の Notebook の設定セルで変更できます）:

- データ: `configs/demo_park.json`（架空、8施設・2ショー・食事1）、季節・混雑は設定セルの値（標準は `busy`）
- 予算: 0円、1000円、2000円（1人分）
- 必須ショーの条件（`EXPERIMENT_SHOW_VARIANTS`）:
  - ショーなし（基準）: S1 を一日の予定から外す（`"exclude": True`）。固定時刻の予定がない基準です
  - 元の公演回（11:00・15:00）
  - 13:00 の回だけ（時刻を変える）
  - パークの奥で開演（場所を変える）
  - 参考: `"required": False` にすると、ショーは必須でなくなりますが、希望度があるので任意の予定として選ばれることがあります（固定時刻の予定がない基準にはなりません）。`"required": True` にすると、そのショーを必須にします
  - 「ショーなし（基準）」で希望順位（`preference_rank`）を使っている場合は、ほかの活動の希望度が変わらないように、元の順位で決まる希望度を明示してからショーだけを除きます
- 方法Bの基準時刻: 入園時刻（`REFERENCE_TIME` で変更可）

任意の一括実験（`RUN_RANDOM_BATCH = True` のときだけ実行）: 乱数の seed で施設の配置・希望度・待ち時間を変えたパークを作り（`generate_random_scenario`）、予算を変えて比べます。

## 5. 記録する値

ケースごと・方法ごとに1行で、次の値を CSV（`comparison.csv`）に保存します。設定は `settings.json` に保存します。

- 設定: ケースID、seed、シナリオ名、季節、入退園時刻、予算、ショーの条件、必須ショー、制限時間、並列数、ソルバーの乱数
- 結果: 状態、最適性の確認範囲、希望度合計、追加費用、移動時間、行列の待ち時間、出口への到着、訪問数、使った短縮利用の施設と枠、見たショーの公演回（`shows_attended`）、訪問した活動の順番（`visited_activities`）、予定に入らなかった施設（`skipped_attractions`）、計算結果の説明（`message`）
- ソルバー: 優先順位の各段階（希望度合計・追加費用・移動時間）の終了状態・目的値・限界値・計算時間、補助の段階の終了状態、計算時間の合計
- 方法B: 候補の施設、基準時刻、候補が方法Aと同じ選択肢になったか（`b_same_options_as_a`。Aに予定がない場合は空欄）
- 検証関数による確認の結果
- 希望度合計の差（A − B, `score_diff_A_minus_B`）、希望度合計が同じで両方の追加費用まで最適性を確認できた場合の追加費用の差（B − A, `cost_diff_B_minus_A`）、差の注記、予定がない場合の理由（`reason`。事前チェックで分かった場合はその内容）

Notebook では、この表を日本語の列名（`comparison_view()`）で表示します。CSV の列名は英語のままです。

## 6. 結果の扱い

- 差は**絶対差（希望度合計の A − B）**を基本にし、比率は使いません。比率を使う場合は、最適値が0のときの扱いを先に定義してください。
- 差は、方法Aと方法Bの**両方で希望度合計の最適性を確認できた場合だけ**計算します。どちらかが暫定案・未判定のときは計算せず、注記を残します（ソルバーの打ち切りの影響が混ざるため）。方法Aの最適性が未確認の値を「真の最適解からの差」として表示しません。
- タイムアウト・実行不可能・入力エラーのケースも除外せず、状態と理由（`reason`。詳しい説明は `message`）とともに表に残します。1つのショーの条件の中身の誤り（存在しないショー・時刻の書き方など）は、そのケースのエラーの行になります。ケースの一覧を作れない設定の誤り（label の重複、予算がリストでない、基準時刻の書き方など）は、計算を始める前に日本語で説明して止まります。
- `b_same_options_as_a` が True のケースは、方法Bの候補が予算内で買えるすべての施設を含み、方法Aと同じ問題になっています（差は構造上0）。
- 行列の待ち時間や出口への到着時刻は、返された予定の値です。補助の段階で最適性を確認できなかった場合は、最小化されているとは限りません。

## 7. 考察の進め方

1. まず「ショーなし（基準）」と各ショー条件で、予算ごとに、方法Aの希望度合計・予定に入った（外れた）施設・使った短縮利用の施設と枠・追加費用がどう変わるかを見ます。
2. 方法Aと方法Bの差が大きいケースと、差がないケースを並べ（Notebook の「代表的なケース」）、予定表で「どの施設の短縮利用を使ったか」「ショーの前後に何を回ったか」「どこで待ったか」を比べます。
3. 差の理由を、基準時刻の待ち時間と、実際に並んだ時刻の待ち時間の違い、ショーの時刻・場所による制約などから説明します。
4. 予算・季節・基準時刻を変えて、同じ傾向が見られるかを確かめます。一括実験では、施設配置などを変えた複数のパークで、差が生まれる条件を探します。

## 8. 発展の例

- 方法Bの規則を変える（基準時刻を昼にする、待ち時間の最大値を使う、など）
- 短縮利用の購入の規則（次に購入できる時刻、購入できる数）を `purchase_rules` としてモデルに加える
- 待ち時間表を、自分で調べた値に差し替える（出典の種類と確認日を記録する）
- 複数の日・複数のグループ、雨天などの不確実性を扱うモデルへの拡張
