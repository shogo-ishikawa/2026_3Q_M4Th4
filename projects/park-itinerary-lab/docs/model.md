# モデルの説明

この文書は、Park Itinerary Lab の入門モデル（01）と本体モデル（02）の内容、時刻の意味、仮定、範囲をまとめたものです。コードの正本は `src/park_itinerary_lab/` にあります。

## 1. 目的と範囲

出発点は「テーマパークでの一日の回り方を提案したい」という希望です。初版では、特定のパークに依存しない一般化した「訪問計画問題」として、次の範囲を扱います。

- 1人、または全員が同じ行動をとる1グループの、1日・1本の経路
- 各施設・各ショー・各食事は最大1回
- 時間帯別の待ち時間表に基づく、決定論的なモデル（1分単位）

新しい問題やアルゴリズムを考案したものではありません。既存の手法（0/1整数計画、制約プログラミングによる経路と時刻の同時決定、優先順位つき最適化）を組み合わせ、学生が問題設定・検証・比較・考察を経験するための土台です。

## 2. 数値の表し方

| 量 | 入力での書き方 | 計算での表し方 |
| --- | --- | --- |
| 時刻 | `"09:30"`（24時間表記） | 0:00 からの経過分（9:30 → 570）の整数 |
| 時間帯 | `"10:00-11:00"` | [開始, 終了) の整数範囲（10:00〜10:59） |
| 所要時間・待ち時間・移動時間 | 分（整数） | 分（整数） |
| 費用 | 円（整数） | 円（整数）。初版の標準は**1人分** |
| 希望度 | 0以上の整数 | 0以上の整数 |

境界の扱いは次のとおりです。

- 時間帯（待ち時間表の時間帯、短縮利用の枠、通常利用の案内時間、食事の開始時間帯）は**開始を含み、終了を含みません**。例えば枠 `10:00-11:00` なら 10:59 に並び始めるのは枠内、11:00 ちょうどは枠外です。待ち時間表で 11:00 に並び始めると、次の時間帯の待ち時間になります。
- 退園時刻は「この時刻までに出口に着く」期限で、ちょうど着くのは成立です。施設の完了期限（`finish_by`）も「以下」です。
- ショーは「開演の `arrive_before_min` 分前（集合時刻）までに到着」していれば成立で、集合時刻ちょうどの到着は成立です。

費用は `cost_basis`（`per_person` = 1人分、`group_total` = グループ総額）で基準を明示します。料金と予算は同じ基準で入力します。`party_size` は「1人分 × 人数」の参考表示だけに使います。

希望順位 `preference_rank`（任意）を指定した場合、n 件のうち k 位の活動の希望度を n − k + 1 とし、一覧にない活動の希望度を 0 にします。順位を得点に変える方法は一つの仮定であり、他の変換も考えられます。`preferences`（希望度の上書き）と `preference_rank` を同時に指定すると、どちらを使うか決められないため入力エラーにします。

入力の誤り（不明な設定項目、時刻の書き方、存在しないID、リストや辞書の形の誤り、未実装の購入ルールなど）は、計算を始める前に日本語の説明つきで「モデルまたは入力のエラー」として返します。

## 3. 入門モデル（01, PuLP）と本体モデル（02, CP-SAT）の違い

入門モデルは「どの活動を選ぶか」だけを決める0/1ナップサック型の問題です（`intro.py`）。

- 決定変数: $x_i \in \{0,1\}$
- 目的: $\max \sum_i p_i x_i$（希望度の合計）
- 制約: $\sum_i t_i x_i \le T$、$\sum_i c_i x_i \le B$、必須の活動 $x_m = 1$

所要時間は待ち時間を含めた固定値で、移動・時間帯で変わる待ち時間・ショーの開演時刻を省きます。したがって、時間の合計が上限以下でも、実際の一日の予定が成立するとは限りません。本体モデルは、訪問順と時刻まで同時に決める別の問題です。両者が一般に同じ答えになることは期待しません（比べるなら、移動ゼロ・待ち時間一定・時間帯の制約なしのように、同じ問題に縮退させた場合に限ります）。

所要時間・希望度・費用がすべて0の任意の活動は、目的にも制約にも現れないため、CBC は値を返しません（`pulp.value` が None）。選んでも選ばなくても実行可能性と希望度の合計は変わらないので、「選ばない」と決めています（`intro.is_chosen`）。必須の活動は「= 1」の制約で値が決まり、それ以外で値がない場合は止めて知らせます。

PuLP 4 では CBC が本体に含まれないため、`pulp[cbc]`（cbcbox）で導入し、`pulp.COIN_CMD(msg=False)` を明示して使います。変数は `problem.add_variable(...)` で作ります。

## 4. 本体モデル（`model.py`）

### 4.1 活動と利用案

活動は施設（attraction）・ショー（show）・食事や休憩（meal）の3種類で、それぞれに「利用案」（`options.py`）を作ります。利用案は「並び始める時刻 q の範囲、待ち時間、費用」の組です。

| 利用案 | q の範囲 | 待ち時間 | 追加費用 |
| --- | --- | --- | --- |
| 通常利用（時間帯ごと） | 待ち時間表の時間帯 ∩ 通常の案内時間 [queue_open, queue_close) | その時間帯の値 | 0 |
| 短縮利用（枠ごと） | 枠 [開始, 終了) | 残る待ち時間（residual） | 仮定枠は料金、取得済み枠は0 |
| ショー（公演回ごと） | 集合時刻（開演 − arrive_before）ちょうど | arrive_before（開演前の待機） | 0 |
| 食事・休憩 | 開始できる時間帯 | 0 | 0 |

通常利用の待ち時間は、**並び始める時刻 q が入る時間帯の値**です。計算を始めた時点の待ち時間を一日中使うことはしません。同じ体験なら、通常利用でも短縮利用でも希望度は同じです。

### 4.2 決定変数

記号は 01・02 の Notebook と同じです: 活動 $a$ の希望度 $p_a$、体験時間 $d_a$、地点 $u$ から $v$ までの移動時間 $\tau_{uv}$（最短の道順で歩いたときの所要時間、分）、利用案 $o$ の待ち時間 $w_o$ と料金 $c_o$。

- $x_a \in \{0,1\}$: 活動 $a$ を行うか
- $y_{a,o} \in \{0,1\}$: 活動 $a$ で利用案 $o$ を選ぶか（$x_a = \sum_o y_{a,o}$）
- $q_a$: 並び始める（集合する・開始する）時刻
- $z_{u,v} \in \{0,1\}$: 地点 $u$ の次に地点 $v$ へ行くか（入口・出口を含む）

### 4.3 制約

| まとまり（関数） | 内容 |
| --- | --- |
| `add_activity_variables` | $y_{a,o} = 1$ なら $q_a$ は利用案 $o$ の範囲内。終了 $e_a = q_a + w_o + d_a$ |
| `add_route_constraints` | AddCircuit で、入口 → 選んだ活動 → 出口 の1本の経路にする（行わない活動は自分自身への辺で外す。孤立した周回や重複訪問は作れない）。$z_{a,b} = 1$ なら $q_b \ge e_a + \tau_{ab}$。最後の活動から出口へも移動し、出口への到着 ≤ 退園時刻 |
| `add_budget_and_required` | 追加費用の合計 $\sum_{a,o} c_o y_{a,o}$ ≤ 予算。必須の活動は $x_a = 1$（取得済み枠を `must_use` にした施設は、その枠での利用が必須） |
| `add_redundant_constraints` | 解を変えずに最適性の証明を速くする制約（4.5） |

到着後すぐに並ばず待つこと（意図的な待機）は、$q_b$ が到着時刻より後でもよいことで表します。これにより、待ち時間が下がる時間帯や枠・開演を待つ予定もモデルに含まれます。予定の重なり、予算超過、退園時刻への遅れは許しません。短縮利用の体験終了が枠内に収まる必要はありません（枠は並び始め＝入場の時刻に適用します）。

移動時間は、座標（縦横の道に沿った距離、分速60m、端数切り上げ）か、入力した表から求め、さらに「途中の地点を通り過ぎてもよい」最短の値に直して使います（表の値より別の地点経由のほうが短い場合は、警告を出して置き換えます）。

### 4.4 目的と優先順位

1. 希望度合計を最大化
2. 1 の最適値を固定し、追加費用を最小化（予算を使い切ること自体は目的にしません）
3. 1・2 を固定し、移動時間の合計（入口から最初、最後から出口までを含む）を最小化
4. 補助: 1〜3 を固定し、出口への到着時刻を最小化

各段階は新しい CpSolver で解き、前の段階が OPTIMAL（目的値 = 限界値の整数）で終わったときだけ値を固定して次へ進みます。CP-SAT の `relative_gap_limit` と `absolute_gap_limit` は0にします（初期値の absolute_gap_limit = 1e-4 を明示的に0へ）。また `cp_model_probing_level` を0にして、前処理の probing を使いません。OR-Tools 9.15.6755 では、冗長な NoOverlap 制約（4.5）を含むまれな極小の例で、probing の内部チェックが Python ごと停止させる（Colab ではカーネルが止まる）ことを確認したためです。この設定は解く速さだけに関わり、解と最適性の証明の正しさは変わりません（乱数の極小問題 2万個で停止しないこと、そのうち 4000 個で独立な正解器と一致することを確かめました。`docs/validation.md`）。補助の段階 4 は、同点の予定の中から無駄な待機の少ない予定を選ぶためのもので、状態の表示（最適性の確認範囲）には影響しません。

必須でなく希望度が0の活動は、予定に入れても希望度が増えず、移動時間も（最短の移動時間を使うため）短くならないので、モデルから外します。研究の比較でショーを除く条件（`exclude_all_shows`・`exclude`、`docs/research-plan.md` の4節）は、この性質を使って、除くショーを必須から外し、希望度を0にします。ショーの場所は地点として残すので、ほかの地点の間の移動時間は変わりません。

ソルバーが返した予定は、同じ訪問順・同じ利用方法のまま、各項目が最も早く終わる並び始めの時刻に直してから返します（時間帯の選び直しを含む）。前の項目が早く終われば後の項目は待てば元の時刻にもできるので、成立性と目的の値は変わりません。

### 4.5 冗長な制約（証明を速くするため）

いずれも、成立する予定を1つも除かないことを確かめたうえで加えています。

- 利用案の範囲を、入口からの最短移動・出口までの最短移動・完了期限・予算で狭め、成立しない利用案を除く。
- どの利用案でも間に合わない移動（$a$ の最も早い終了 + 移動 > $b$ の最も遅い並び始め）の辺を作らない。
- 活動ごとの区間 [並び始め − その活動へ来るための最小の徒歩時間, 終了) は、どの順路でも重ならない（NoOverlap）。
- 移動時間 + 待ち時間 + 体験時間の合計 ≤ 滞在時間（意図的な待機は0以上）。

設計時の試作では、これらを加えない素朴なモデルは架空の8施設の例で30秒以内に最適性を証明できない場合がありましたが、加えると数秒で証明できるようになりました（`num_workers=8`。2コアに制限した場合も、8 workers のほうが 2 workers より証明できる例が多くなりました）。

### 4.6 結果の状態

| 状態 | 意味 |
| --- | --- |
| 最適性確認済み | 優先順位の3段階すべてで最適性を確認 |
| 実行可能な暫定案 | 予定はあるが、どこかの段階で最適性を確認できなかった（確認範囲: none / score / score_cost を表示） |
| 実行不可能と証明 | 事前チェック（4.7）またはソルバーが、条件を満たす予定がないことを証明 |
| 未判定 | 制限時間内に予定も「予定がない」証明も得られなかった（実行不可能とは表示しない） |
| モデルまたは入力のエラー | 入力の誤り、MODEL_INVALID、検証関数で不一致が見つかった場合など |

結果には、各段階の終了状態・目的値・限界値・計算時間・制限時間、OR-Tools の版、ソルバーの設定を含めます。

### 4.7 事前チェック（`precheck.py`）

最適化の前に、明らかな衝突を調べます。一部の活動だけを取り出し、最短の移動時間を使う「必要条件」なので、ここで成立しないと判定された条件は、どんな予定でも満たせません。

- P1: 入口から出口まで、入退園時刻の間に移動できない
- P2: 必須の活動が、それだけでも成立しない（理由を説明。時間の面では入るが料金が予算を超える場合、完了期限に間に合わない場合（その方法の料金も予算を超えるなら、両方）は、それぞれそう説明）
- P3: 必須の活動の2つ組が、どの順序・どの利用案でも両方は入らない（各利用案の最も早い時刻で判定。待ち時間は到着時刻の値ではなく、利用案の値を使う。時間の面では入るが費用の合計が予算を超える場合は、そう説明）
- P4: 必須の活動の、予算内で使える利用案での最小の待ち時間 + 所要時間の合計が滞在時間を超える（料金を考えなければ、この合計だけは収まる場合は、そのことも書き添える。移動などほかの条件は考えていないので、成立するとは言わない）

事前チェックで原因が見つからず、ソルバーが実行不可能を証明した場合は、原因を断定せずにそう表示します。

## 5. 時刻の意味

1つの施設について、時刻を次のように区別します。

前の場所を出発 → 移動 → **到着** → **意図的な待機（空き時間）** → **並び始め（入列）** → **待ち時間** → **体験開始** → **体験終了**

ショーは、集合時刻（開演の `arrive_before_min` 分前）から開演までを「開演前の待機」、開演から終演までを「鑑賞」とします。食事・休憩は開始時刻から所要時間だけ予定を確保します。

## 6. 短縮利用（有料の時間短縮）の仮定

- **仮定枠（未取得）**: データ（`shortcut_offers`）にある枠は、「取得できる」と仮定して計算します。使った場合だけ、その料金を今回の追加費用に数えます。
- **取得済み枠**: 条件（`acquired_shortcuts`）で入力します。追加費用は0円で、既払い額（`paid_yen`）は別に表示し、二重に数えません。費用は「既払い額」「今回の追加費用」「総額」を分けて表示します。`must_use`（必ず使う／使うかどうかを任せる）は利用者が必ず指定し、勝手に必須にはしません。
- 予算（`budget_yen`）は、これから支払う追加費用に適用します。予算0円・短縮利用を検討しない（`allow_new_shortcuts = False`）場合も動きます。
- 実際の購入、抽選、在庫確認、非公開APIへの接続、公式アプリの自動操作は行いません。
- 現在の制度を完全に再現したものではありません。初版では、次に購入できる時刻、購入できる数の制限、売り切れ、無料の案内などを扱いません（モデルの仮定）。追加の購入ルールは `purchase_rules` として将来拡張できる形にしてありますが、初版では何も実装しておらず、指定すると入力エラーになります。

## 7. 一般化モデルの範囲と限界

- 待ち時間は時間帯別の表に基づく決定論的なモデルです。結果は**この1分単位のモデルの厳密解**であり、実際の将来の待ち時間を保証するものではありません。時間帯の境目で待ち時間が急に変わるため、「1分待つと待ち時間が大きく減る」ような予定が出ることがあります。
- スコアは入力した希望度の合計であり、実際の来園者の満足度を測った値ではありません。
- 同じショーの公演はすべて同じ場所で行うと仮定します。食事・休憩は決まった場所で行います。
- 施設の故障・天候・混雑の予測誤差・体力・同行者ごとの違いなどは扱いません。
- 目的の値が同点の予定が複数ある場合、どれが返るかは並列計算の都合で変わることがあります（目的の値は同じです）。

## 8. 検証の仕組み

- `validate.py`（検証関数）: 返された訪問順・利用方法・並び始めの時刻だけから、移動・待ち・終了時刻・費用・必須条件を計算し直します。`model.py` や `options.py` を使わず、待ち時間表の引き方も別に書いています。`solve_day_plan()` は返す前にこの検証を行い、制約違反やソルバーの値との不一致があれば「エラー」にして、その予定は返しません（理由は `messages`、計算し直した値は `validation` に残します）。
- `bruteforce.py`（独立な正解器）: CP-SAT を使わず、すべての訪問順・利用方法・並び始めの時刻（1分ごと）を調べる全時刻の探索で、極小問題の最適値を求めます。標準ライブラリだけを使い、作品の他のモジュールを読み込みません。Notebook からも照合できるよう `src/` に置いています（テストは `tests/` にあります）。

実際に行った確認と結果は [validation.md](validation.md) にまとめています。

## 9. 判断理由（指示で決まっていなかった細部）

| 項目 | 選んだ方法 | 理由 |
| --- | --- | --- |
| 時刻の表し方 | 0:00 からの分 | 入力の「時:分」と1対1に対応し、日をまたがない範囲で十分なため |
| 徒歩の距離 | 縦横の道に沿った距離・分速60m・切り上げ | 園内の通路は直線で結ばれないことが多く、混雑時の歩行を遅めに見込むため。切り上げても三角不等式は保たれる |
| 移動時間の表 | 最短経路に置き換える | 入力した表で別の地点経由のほうが短い場合、その地点で何もせず通り過ぎられるため |
| 希望度0の任意の活動 | 予定に入れない | 目的の値が変わらず、意味のない寄り道を避けるため |
| 補助の段階 | 出口への到着時刻を最小化 | 同点の予定の中から、無駄な待機の少ない読みやすい予定を選ぶため。状態の表示には影響させない |
| ソルバーの並列数 | 8（2コアでも） | 試作で、2コアに制限しても 8 workers のほうが最適性を証明しやすかったため |
| 制限時間 | 各段階20秒 | デモが Colab のCPUで十分に終わり、難しい場合は「暫定案」と分かるため |
| 費用の基準 | 1人分 | 指示の標準。グループ総額は参考表示 |
| 順位から希望度 | n − k + 1 | 単純で説明しやすい。ほかの変換もあり得ることを明記 |
| 方法Bの規則 | 基準時刻（標準は入園時刻）の「短縮できる時間 ÷ 料金」で予算内の候補を選ぶ | 情報が少ない時点で先に決める判断を表すため（[research-plan.md](research-plan.md)） |
| 正解器の場所 | `src/park_itinerary_lab/bruteforce.py` | Notebook から呼べるようにするため（指示の推奨構成では tests/）。独立性はテストで確認 |
| Notebook の出力 | 出力を消してコミット | 生成物をコミットしないため。実行の確認は `scripts/run_notebooks.py` |
