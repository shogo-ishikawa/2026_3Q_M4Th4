# WORLD DEFINITIONの仕組みを読んでみよう

物体の性質を変えると、通れる場所だけでなく、その先の装置も変わります。まず一つの謎を遊び、「この操作で何が変わったか」をコードの中で探してみましょう。全てのファイルを最初から読む必要はありません。

## 1. 画面、状態、描画を分ける

`index.html` はボタンや画面の置き場所、`style.css` は色や大きさを扱います。`engine.js` はルールと移動、`mystery.js` は謎解き編のマップと装置の関係を扱います。`app.js` が入力を受け取り、`renderer.js` が現在の状態を描きます。

状態は「今どうなっているか」を表すデータです。位置ならJavaScriptで次のように書けます。

```js
const player = { x: 100, y: 200 };
player.x = player.x + 5;
```

横方向の位置を5だけ増やす例です。Pythonの辞書と似ていますが、JavaScriptでは `player.x` のように値を取り出せます。

## 2. 謎を「装置のつながり」として表す

謎解き編4面は `mystery.js`、以前の練習9面は `engine.js` のデータにあります。位置だけでなく、レバー、水路、扉、調べられる石碑などもデータとして持ちます。

```js
// データの読み方を示す例です。
const river = { x: 300, y: 200, w: 100, h: 700 };
```

`x` と `y` は左上、`w` と `h` は幅と高さです。画面では右へ進むとxが増え、下へ進むとyが増えます。

水車を題材にすると、「水を渡る」と「水車を動かす」は異なる条件です。水を凍らせれば歩けますが、流れは止まります。水門を開き、水の定義を解除すると、今度は流れを使えます。一つの操作が全てに都合よく働かないことが、順番を考える理由になります。

次は同じ考え方をPythonで表した例です。ゲームの処理をそのまま写したものではありません。

```python
water_frozen = True
sluice_open = True
water_flows = sluice_open and not water_frozen
print(water_flows)  # False

water_frozen = False
water_flows = sluice_open and not water_frozen
print(water_flows)  # True
```

`and` と `not` だけでも、二つの条件の関係を表せます。「どの変数を変えれば扉が開くか」を、変数と条件式へ対応させてみてください。

## 3. 画面と当たり判定で同じ状態を使う

水がないように見えるのに進めなかったり、閉まった扉を通れたりすると、見た目から謎を考えられません。そこで、現在の定義やレバーの状態から、その時点の水路と壁を求めます。

`physicalState(game)` は有効な水面、閉じた扉を含む壁、流れや装置の状態を返します。移動の判定と描画が同じ情報を見ることで、装置が動いて通路が変わったことを確かめられます。`puzzleStatus(game)` は画面の仕掛け一覧、`notebook(game)` は調べた手掛かりを返します。

装置を作動させる条件と、作動したように描く条件を別々に書くと、修正したときに食い違いやすくなります。絵の変化にも、次の操作を判断できる情報を持たせましょう。

## 4. 移動する前に「通れるか」を調べる

位置をすぐ書き換えると壁を通り抜けてしまいます。次の位置を計算し、そこへ進めるか調べます。

```js
// 処理の考え方を示す例です。
const nextX = player.x + 5;
if (nextX < 300) {
  player.x = nextX;
}
```

`walkable()` は、その時点の壁、水面、足場、物体を調べます。物体を運ぶときも、プレイヤーが動けることと、物体自身が壁を通れることの両方が必要です。プレイヤーが通れる入口でも、大きな石を運べるとは限りません。

浮遊物体を先に動かした結果、プレイヤーの足場がなくなる場合は元へ戻します。物体の大きさや向きを変えるときも、足場や壁との重なりを確認します。

石と木が近くにある場合は、研究室で選んだ近くの浮遊物体を優先して運びます。選んだ物体が遠ければ、近い方を使います。

## 5. 定義の適用と解除を一つの変更として扱う

定義は物体ごとに残ります。木の発光を適用した後で水を凍らせても、木の光は消えません。同じ物体への再適用は、その物体のルールの置き換えです。

`applyRule()` は対象、使える動作、最大3つという制約、未解放や矛盾などを確認します。`clearRule()` は選んだ対象のルールを `null` へ戻します。解除した物体が世界から消えるわけではありません。

水が元へ戻ると流れ、石の浮遊を解除すれば地面へ戻ります。運ぶときの条件と、重さの仕掛けを押すときの条件は違います。解除も、世界に働きかける一つの操作として扱います。

変更後の仮の状態でプレイヤーや物体が安全かを確認し、足場を失う場合や壁へ重なる場合は元へ戻します。先にルールを消してから安全性を調べないと、失敗を表示しても世界が変わったままになってしまいます。

## 6. 調査と暗号を状態へ記録する

看板や石碑は、近づいてEを押すと調べられます。明かりが必要な文字なら、光の状態も確認します。読んだ内容は手帳へ残すため、後の部屋で読み返せます。

同じキーを押し続けただけで暗号が何回も入力されないよう、「Eが離れていた状態から押された」という変化を使います。移動しながらEを押す運搬とは操作を分けます。

暗号の進み具合や、どの石碑を読んだかはゲームの状態です。一方、石碑の本文や正しい並びはステージのデータです。両方を分けておくと、途中保存へプログラムやステージ定義そのものを入れずに済みます。

## 7. 広い世界と、画面に映る範囲を分ける

謎解き編は一画面より広いマップです。`worldBounds(game)` で世界の範囲を求め、描画側のカメラがプレイヤーを追います。カメラが動いても、物体の座標や当たり判定は世界の座標のままです。

```python
world_x = 1200
camera_x = 900
screen_x = world_x - camera_x
print(screen_x)  # 300
```

これは世界のx座標1200の物体を、画面のx座標300へ描く考え方です。全体地図では同じマップを縮小し、現在地と部屋のつながりを確かめられるようにします。文字まで小さくして読ませる表示と、近づいて調べる表示は役割が違います。

## 8. 状況からヒントを選ぶ

`hints(game)` は段階別の文章、`hintKey(game)` は現在の局面、`hintTarget(game)` は任意の目印を返します。どの面かだけでなく、読んだ手掛かり、定義、装置、立っている場所を見ます。

最初は考え方を示し、必要に応じて具体的な手順へ進めます。常に答えを表示するより、見つけた変化から考える余地を残せます。正解を隠しすぎて操作できなくなることも避けるため、近くでできるE操作は別に案内します。

練習ステージにも、足場が短い場合の案内、物体の配置復旧、ゲートへ向かうヒントがあります。

## 9. 戻す状態と保存する状態を決める

定義の適用や解除、ひと続きの運搬、Eでの調査や装置操作を始める前に状態を記録すると、Zで試した方法を戻せます。毎フレームを履歴に入れると、一度の運搬を取り消すために何百回も戻す必要が出ます。

状態をコピーするときは、二つの履歴で同じ物体を共有しないようにします。Pythonでも、辞書の代入だけでは中身を共有することがあります。

```python
import copy

before = {"stone": {"x": 100, "y": 200}}
after = copy.deepcopy(before)
after["stone"]["x"] = 300
print(before["stone"]["x"])  # 100。元の状態は残ります。
```

`session.js` は位置、ルール、手掛かり、装置の途中の状態を保存します。ステージの形や処理は保存せず、エンジンの信頼できるデータから復元します。新しい謎解き編では広い座標を使うため、保存の検査も、そのステージの範囲と合っているかを調べます。

解放状況とベスト記録は `progress.js`、途中の状態は `session.js` で別に管理します。新しい途中保存と旧版の途中データも分け、旧データを削除しません。Zで戻す履歴は今開いているゲームの中だけに残り、再読み込み後には引き継ぎません。

保存できない環境でも操作を続けられること、壊れたデータやその版で使えない状態を読み込まないことも確かめます。

## 10. ローカルAIは候補を作る

任意のローカルAIでは、文章を対象と動作の候補へ変換します。

```json
{"target": "stone", "effects": ["grow", "float"]}
```

プレイヤーが候補を確認して適用すると、通常の選択と同じ `applyRule()` を通します。文字列をプログラムとして実行する仕組みではありません。効果と操作の説明は確定したゲーム処理を使い、名前の生成を待つ間も次の操作を続けられます。

遅れて届いた返答が、別のステージや新しい定義を上書きしないよう、どの状態への返答なのかを照合します。定義の解除は画面の専用操作で行えます。

## 11. 小さく変更して、解法を確かめる

| 試すこと | 予想してみること | 確かめること |
| --- | --- | --- |
| 水路や水門の位置を変える | 別の部屋へ流れを届けられるか | 水の表示と通行判定が一致するか |
| 装置の条件を一つ変える | 定義を変える順番はどうなるか | 手掛かりから条件を推測できるか |
| 手掛かりの場所を変える | 探索の順番は変わるか | 必要な文字を調べに行けるか |
| 狭い入口を作る | 縮小や解除が必要になるか | 物体とプレイヤーが安全に通れるか |
| 橋の向きを変える | 別の方向へ渡れるか | 描画と足場の向きが一致するか |
| 目印を消す | 地図と看板で場所が分かるか | 必要な操作まで隠していないか |

色や数値だけを変えても、順番を考える理由が増えるとは限りません。どの操作が何を変え、それが次の装置へどうつながるかを確認します。

`tests/mystery.test.js` は謎解き編、`tests/engine.test.js` はルールや練習面の進行を確かめます。攻略は開始位置から通常の入力で進め、装置が条件なしに開かないこと、誤った順序から戻せること、解除後にも道が残ることを確認します。実際の表示でも、水の流れや扉、手掛かりが判断できるか確かめてください。

実Ollamaによる文章の解釈・名前の生成と、元のC++参照版のビルドは未確認です。模擬応答の検証と実機での確認は区別して記録してください。
