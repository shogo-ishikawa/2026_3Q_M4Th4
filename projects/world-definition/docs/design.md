# WORLD DEFINITIONの仕組みを読んでみよう

この作品では、「プレイヤーがどこにいるか」と「その場所を通れるか」を組み合わせてゲームを動かしています。最初から全てを読む必要はありません。まず一つのルールを使って遊び、その動作がコードのどこに書かれているかを探してみてください。

## 1. 画面とゲームの状態を分ける

`index.html` にはボタンやゲーム画面の置き場所、`style.css` には色や大きさがあります。`engine.js` はプレイヤーの位置、川、物体、結晶、ゲートなどを扱い、`app.js` が入力を受け取り、その状態をCanvasに描きます。

ゲームの状態は「今どうなっているか」を表すデータです。例えば位置を表すデータは、JavaScriptでは次のように書けます。

```js
const player = { x: 100, y: 200 };
player.x = player.x + 5;
```

これは、横方向の位置を5だけ増やす例です。Pythonの辞書と似ていますが、JavaScriptでは `player.x` のように名前をつなげて値を取り出せます。

## 2. 移動する前に「通れるか」を調べる

方向キーを押したとき、すぐに位置を書き換えると壁を通り抜けてしまいます。そのため、「次の位置」を計算し、そこへ移動してよいかを調べます。

```js
// 処理の考え方を示す例です。
const nextX = player.x + 5;
if (nextX < 300) {
  player.x = nextX;
}
```

この例では、横の位置が300未満のときだけ移動します。ゲームでは、壁・川・物体の状態なども条件に加えています。`engine.js` で川の判定を探し、水の「凍結」や「固体化」があると、通れる条件がどう変わるかを読んでみましょう。

## 3. 動詞は、決めた処理につなぐ

研究室で選んだ動作は、あらかじめ用意したゲーム処理につながります。例えば水の凍結は川の通行条件を変え、石の浮遊は石を運んで足場に使えるようにします。選んだ文章をプログラムとして実行する仕組みではありません。

物体ごとにルールを保持するため、水のルールを作った後で炎のルールを変えても、川を渡れる状態が残ります。同じ物体への適用は置き換えです。足場の上で、その足場をなくす変更が起きないかも確認します。

この分け方により、「表示された能力名」と「実際に変わるゲームの状態」を照らし合わせて考えられます。任意のローカルAIが担当するのは名前と説明の補助で、効果の内容はゲーム側で確認します。

## 4. 小さく変更して比べる

変更前のファイルを残し、一度に一つだけ変えてみましょう。

| 試すこと | 予想してみること | 確かめること |
| --- | --- | --- |
| プレイヤーの色を変える | 背景から見つけやすくなる色はどれか | 草・川・足場の全てで見えるか |
| 移動の速さを変える | 速いほど遊びやすくなるか | 斜め移動や壁際で操作しにくくならないか |
| 石の大きさを変える | 大きいほど川を渡りやすくなるか | 見た目と当たり判定が一致するか |
| 川や結晶の位置を変える | 複数のルールで攻略できるか | 最後まで進める道が残るか |

見た目だけを変えたつもりでも、当たり判定まで変える必要があるかもしれません。変更後は最初からゴールまで遊び、想定した動作と実際の動作を比べます。

## 5. 確認する理由を考える

`tests/engine.test.js` は、描画を使わずにゲームの処理を確かめます。例えば「ルールなしで川を渡れない」「ルールを適用すると渡れる」「結晶を取る前に加熱できない」という、遊びの約束を確認することが大切です。

テストが通っても、説明の読みやすさやボタンの押しやすさまでは分かりません。コードによる確認と、実際に操作する確認を組み合わせてください。AIに変更を依頼するときも、「何を変えたいか」「元のどの遊びを残したいか」「何を確認すれば成功か」を具体的に伝えると、結果を判断しやすくなります。
