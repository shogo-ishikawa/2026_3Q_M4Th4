# WORLD DEFINITIONの仕組みを読んでみよう

この作品では物体の性質を変えると、その場所でできることも変わります。最初から全てのコードを読む必要はありません。まず一つの動作を使って遊び、画面に現れた変化をコードの中で探してみましょう。

## 1. 画面、状態、描画を分ける

`index.html` にはボタンやゲーム画面の置き場所、`style.css` には色や大きさがあります。`engine.js` は世界の状態とゲームの約束を扱います。`app.js` が入力を受け取り、`renderer.js` が現在の状態をCanvasへ描きます。

ゲームの状態は「今どうなっているか」を表すデータです。位置ならJavaScriptで次のように書けます。

```js
const player = { x: 100, y: 200 };
player.x = player.x + 5;
```

これは横方向の位置を5だけ増やす例です。Pythonの辞書と似ていますが、JavaScriptでは `player.x` のように名前をつなげて値を取り出せます。

## 2. ステージをデータで表す

基本5面と応用4面、計9つのステージは `engine.js` の `LEVELS` にまとめています。川や壁の位置、ゴール、物体、受信盤などの配置をデータとして持ち、移動や判定の処理は共通で使います。

例えば、位置と大きさが決まった川は次のように表せます。

```js
// データの読み方を示す例です。
const river = { x: 55, y: 350, w: 760, h: 80 };
```

`x` と `y` は左上の位置、`w` は幅、`h` は高さです。画面では右へ進むとxが増え、下へ進むとyが増えます。川を広げたら、その川を渡れる足場や別の経路も用意する必要があります。

同じ処理をステージごとに複製するより、配置を変えたときの影響を追いやすくなります。ただしデータを変えれば必ず面白くなるわけではありません。最後まで遊び、考えた解法が実際に成立するか確かめてください。

## 3. 移動する前に「通れるか」を調べる

方向キーを押したときに位置をすぐ書き換えると、壁を通り抜けてしまいます。そのため次の位置を計算し、移動してよいかを調べます。

```js
// 処理の考え方を示す例です。
const nextX = player.x + 5;
if (nextX < 300) {
  player.x = nextX;
}
```

ゲームの `walkable()` は壁、川、物体、足場を条件に加えています。水が凍っている場合と石の足場がある場合では、通れる理由が異なります。川の判定を読み、それぞれの条件がどこで確認されるか探してみましょう。

浮遊物体を運ぶときはプレイヤーの足場も動きます。物体を先に動かした結果、プレイヤーが支えられなくなる場合は元の位置へ戻します。同じ理由で、足場の上にいる間はその足場を失う再定義を受け付けません。

応用面では、運ぶ物体自身も壁にぶつかります。プレイヤーが通れる入口でも、石が大きすぎれば運べません。縮小して通し、広い場所で成長させ直すという手順に意味が生まれます。物体を運ぶときだけでなく、大きさや向きを変える再定義でも、壁や足場への影響を確認します。

石と木が近くにあるときは、研究室で選んだ浮遊物体を優先して運びます。選んだ物体が運べる範囲にない場合は、近い浮遊物体を選びます。「一番近いもの」だけで決めるよりも、プレイヤーが今扱いたい対象を反映できます。

## 4. 同じ形を描画と当たり判定に使う

物体が大きく見えているのにすり抜けられたり、炎から離れて見えるのに触れた扱いになったりすると、遊ぶ人は判断できません。そこで物体の位置と大きさを共通の関数から求めます。

- `objectGeometry()`：石や木の位置、大きさ、浮遊による高さ。
- `bridgeGeometry()`：川に置いた足場の長方形。
- `fireGeometry()`：炎の移動位置、大きさ、消火状態。

`renderer.js` はこれらの値を使って描き、`engine.js` は同じ値から接触を調べます。光や波紋のような装飾は別に描けますが、当たり判定まで大きくなったかのように見せない工夫が必要です。

## 5. 動詞を世界の状態につなぐ

研究室で選んだ動作は、用意した処理につながります。水の凍結は通行条件を変え、石の浮遊は運搬と足場を使えるようにします。文章をプログラムとして実行する仕組みではありません。

ルールは物体ごとに保持します。木に「浮遊・発光」を適用した後で炎を「加熱」しても、木のルールは残ります。同じ木に「発光」だけを適用し直すと浮遊は外れます。`applyRule()` が、選んだ動作の数、対象、解放条件、安全な変更かどうかを調べています。

表示の変化にも役割があります。浮遊は物体と影を離し、成長は形を大きくし、縮小は小さくします。回転を含む定義は足場を横向きにし、外すと縦向きへ戻します。発光は光源を作り、脈動は波紋と明滅で表します。定義を適用した瞬間の表示と、適用後に残る表示の両方があると、何を変えたかを追いやすくなります。

成長と縮小を同時に選ぶと、大きさがどちらなのか決まりません。そこで同時には適用できない組み合わせとして扱います。こうした制約は画面だけでなく、状態を変更する関数でも確認します。

ローカルAIモードでは、文章を対象と動作の候補へ変換します。例えば「石を大きくして浮かせたい」から、次のデータを作ります。

```json
{"target": "stone", "effects": ["grow", "float"]}
```

プレイヤーが候補を確認して適用すると、通常の選択と同じ `applyRule()` を通します。AIが返した文字列をプログラムとして実行する仕組みではありません。対象、使える動作、最大3つという制約、未解放や封印などの条件をゲーム側で調べます。効果と操作の説明も、エンジンで確定した情報を使います。

名前の生成は、定義の適用と分けて待ちます。AIの返答が遅れても次の操作を続けられ、古いルールへの返答が新しいルールを上書きしないよう、どの状態への返答かを照合します。

## 6. 受信盤は「場所」と「性質」を調べる

ステージ3以降では、指定された物体を受信盤の近くへ運び、必要な動作を届けます。例えば光の紋章なら木の発光、共鳴盤なら石の発光と脈動が必要です。

判定は、物体が十分近いか、必要な動作が適用されているか、その状態を約1秒間保ったかを調べます。基本面では条件を満たすと盤が点灯し、その記録を保持します。一度作動させた盤から物体を離しても消えません。

応用面の「同時維持」の盤は、現在の配置と動作を毎回調べます。片方を点けてから同じ物体で次を点ける方法では条件をそろえられず、二つの物体に役割を分ける必要があります。出口が開いた後は通路を確保するため、物体を動かしても門を閉じないルールです。

また、材質を調べる盤は、プレイヤーがその場所に立っているかと、水の凍結・固体化のどちらを使っているかを調べます。脈動の受信盤では、明るい位相の間だけ充電を増やします。描画の明滅と、ゲーム側の判定に同じ周期を使うことで、動詞が見た目だけの変化にならないようにしています。

「発光している」という性質だけでなく、光を届ける場所にも意味を持たせることで、ルール選択と移動を組み合わせた問題になります。単にボタンを正しい順番で押すだけでは解けない理由を考えてみてください。

## 7. 失敗から続けられる場所を記録する

炎に触れたとき、橋を動かした後なのに最初の岸へ戻されると、渡る道がなくなることがあります。そこで、川や障害物を避けて立てる岸の位置を、このプレイ中の復帰地点として更新します。炎に触れた場合は、最後の安全な岸へ戻します。その場所を後から物体が塞いだときは、近くの安全な場所を探します。

復帰時もルール、結晶、欠片、点灯した受信盤は残します。「失敗したので位置を戻す」処理だけでなく、「戻った後も操作を続けられるか」を確かめる必要があります。

物体の配置を戻す `recoverObject()` も、ただ座標を最初の値にするだけでは不十分です。プレイヤーが川の上や向こう岸にいるときに橋を初期位置へ戻すと、足場や帰り道がなくなります。そのため、プレイヤーが初期位置と同じ岸にいるときだけ使えます。定義と結晶、記録型の盤の点灯は変えません。同時維持の盤は、その後の配置に応じて点灯を調べ直します。

## 8. 現在の状態からヒントを選ぶ

攻略ヒントは、ステージ番号だけでなく、今のルール、川を渡ったか、結晶や受信盤の状態を見て選びます。`engine.js` の `hints(game)` が段階別の文章、`hintKey(game)` が現在の局面、`hintTarget(game)` が次の目印を返します。近くで使える操作は `interactionStatus(game)` から求めます。

`app.js` はJキーやボタンでヒントを開き、考え方から具体的な手順へ順に表示します。局面が変わったときは、新しい局面の最初のヒントへ切り替えます。目印はプレイヤーが表示を選んだ場合だけ描きます。ヒントの判定をゲームの状態から求めることで、既に済んだ操作を何度も案内するのを避けられます。

## 9. 戻す状態と保存する状態を決める

「1手戻す」には、定義や運搬を始める前の状態を記録します。毎フレームを履歴に入れると、運搬を取り消すために何百回も戻す必要が出ます。そこで、定義の適用、ひと続きの運搬、物体の配置復旧を一つの操作として扱います。`session.js` が履歴を保持し、戻すときにその状態からゲームを作り直します。

状態をコピーするときは、同じ物体を二つの履歴から共有しないようにします。Pythonでも、リストや辞書の代入だけでは中身を共有することがあります。

```python
import copy

before = {"stone": {"x": 100, "y": 200}}
after = copy.deepcopy(before)
after["stone"]["x"] = 300
print(before["stone"]["x"])  # 100。元の状態は残ります。
```

ゲームの途中保存も `session.js` が扱います。位置、適用したルール、結晶や盤などの状態を保存し、再読み込み後に「続きから」で使います。ステージの形や処理そのものは保存せず、`engine.js` のデータを使います。途中データのステージ番号や動作、値の範囲を確認し、その版で安全に読み込めない場合は新しく始めます。

一方、解放済みステージとベスト記録は `progress.js` で管理します。途中の状態をやり直しても、過去のクリア記録は失われません。1手戻すための履歴は今開いているゲームの中だけに残し、再読み込み後には引き継ぎません。

保存は同じブラウザで使うためのもので、別の端末へ自動で共有しません。ブラウザが保存を許可しない場合でもゲームを続けられることと、壊れたデータを読み込まないことを確かめます。

## 10. 小さく変更して比べる

Gitで変更前の状態を残し、一度に一つだけ変えてみましょう。

| 試すこと | 予想してみること | 確かめること |
| --- | --- | --- |
| 浮遊の表示を変える | 高さや影で浮いていると分かるか | 描画と当たり判定が一致するか |
| 移動の速さを変える | 速いほど遊びやすくなるか | 壁際や物体の運搬で操作しにくくならないか |
| 足場の幅と長さを変える | 成長が必要な川を作れるか | 岸と足場の間に通れない隙間ができないか |
| 受信盤の位置を変える | 物体の運び方が変わるか | 必要な物体を実際に届けられるか |
| 必要な動作を変える | 組合せの考えどころが増えるか | 最大3動作で解けるか |
| 橋を回転させる | 別の向きの水路を渡れるか | 描画と足場の縦横が一緒に変わるか |
| 盤を同時維持へ変える | 物体の役割分担が必要になるか | 両方を配置でき、開いた出口へ進めるか |
| 欠片の位置を変える | 少し寄り道したくなるか | 取るために先へ進めなくならないか |

色や数値を変えた後は最初からゴールまで遊びます。遊ぶ人が何を見て判断できるかも確かめてください。

## 11. コードの確認と実際のプレイを組み合わせる

`tests/engine.test.js` は描画を使わず、移動入力を与えてステージの進行を確かめます。「ルールなしで川を渡れない」「受信盤へ違う物体を運んでも作動しない」「必要な条件を満たすと最後まで進める」といった遊びの約束を確認します。

攻略テストは、細い隙間を通れるかだけでなく、目印に沿った自然な進み方でも確かめます。基本5面に加え、縮小、回転、同時維持、材質と脈動を使う応用面も、通常の移動と定義の入力だけでゴールまで進めるか確認します。炎に触れた直後の保護時間で偶然ゴールできても、無傷の攻略が成立したことにはなりません。復帰する位置を物体が塞いでいる場合や、橋を対岸へ動かした後に失敗した場合も確かめます。

入力のテストでは、キーボードと画面ボタンの同時使用、ダイアログ中の停止、1手戻す操作、途中再開、古いAI応答が戻る場合なども扱います。テストが通っても文字の読みやすさや効果の見え方までは分かりません。コードによる確認と実際の操作を組み合わせてください。

実Ollamaによる文章の解釈・名前の生成と、元のC++参照版のビルドは未確認です。模擬した応答でのテストと実機での確認は区別して記録してください。
