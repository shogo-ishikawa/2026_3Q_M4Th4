テストで確かめている主な内容：

- 正弦波（倍音なし）の三和音24種類が、すべての区間で正しいコード名になる
- 無音→コード→無音の境界が 1.0 秒・3.0 秒の位置にそろう／コードの変わり目（2.0 秒）がずれない
- 切り出して解析した結果に、切り出し位置を足すと元ファイルの時刻になる
- 全体が無音の入力は N になり、注意を表示する。2 秒未満や時間幅より短い入力はエラーにする
- しきい値を厳しくすると、N ではなく判定保留（X）になり、候補は残る。判定保留の区間はまとめず、区間ごとの候補と類似度を残す。N（無音）の区間の類似度は値なし（CSV では空欄）
- 評価：完全一致（1.0）、不一致（0.0）、境界が 0.5 秒・1.0 秒ずれた場合（0.875・0.75）、判定保留（不正解として数え、判定率も下がる）、N の区間での判定保留、予測なし、注釈のない時間（評価しない）、予測区間の重なり（エラー。許容範囲内の重なりは二重に数えない）
- 正解と予測がどちらも評価範囲を隙間なく覆い、判定保留を含まない20通りの乱数の例で、評価の値が mir_eval の `majmin` 比較の結果と一致する
- 不正な注釈：列の不足、空のファイル、数値でない時刻、逆転、重なり（対応外のコードの行の後も検出）、対応外のコード、空欄、負の時刻、音源より長い区間、UTF-8 以外の文字コード。問題をファイルの行番号付きでまとめて表示する。列名の前後の空白は受け付ける

## 2. 第1段階：単独音源のコード認識（合成音）

既定の設定での確認です（プログラムの確認であり、実録音の精度ではありません）。

- Karplus-Strong 法の合成音で、24コード × 乱数シード2通り（各3秒、6区間）を解析しました。48通りのうち45通りはすべての区間が正しいコードになりました。残る3通り（C:min、C#:min、F:min）は、6区間のうち1区間が判定保留になり、C:min の1通りではさらに1区間が同主調の C:maj になりました。根音の倍音（5倍音は長3度の音名）の影響と考えられます（推測であり、原因は確かめていません）。
- 合成デモ（`guitar-chord-lab make-demo` で作る各18秒の2本）：`demo_a` は正解率 0.972（判定保留 0.5秒、誤り 0秒）、`demo_b` は正解率 1.000 でした。

### 4.2 GuitarSet の実ギター録音＋合成ドラム（5素材・15混合条件、環境 A）

`guitar-chord-lab guitarset` で取り出した5本（奏者01〜05、各録音の先頭20秒、`third_played_ratio` 0.937〜1.0）に、120 BPM の合成ドラムを混ぜました。同じ内容を CLI と Notebook 3 で実行し、同じ値になりました。

| 条件 | 伴奏 0 dB | +6 dB | +12 dB |
| --- | --- | --- | --- |
| solo（平均 ± 標準偏差） | 0.482 ± 0.225 | 同左 | 同左 |
| mixture | 0.417 ± 0.169 | 0.280 ± 0.190 | 0.161 ± 0.155 |
| separated | 0.485 ± 0.242 | 0.482 ± 0.236 | 0.469 ± 0.231 |
| 分離後 − 分離前（平均、最小〜最大） | +0.068（−0.087〜+0.206） | +0.202（+0.069〜+0.378） | +0.308（+0.129〜+0.716） |

- 全15条件で、混合音・分離音と単独ギターの時間ずれは 0 ms でした。
- 伴奏 0 dB では、分離後に正解率が下がった録音が2本ありました（−0.006、−0.087）。
- 単独ギターでも正解率は録音によって 0.236〜0.726 と大きく異なりました。
- 素材は5本だけで、伴奏は和音を持たない合成ドラムです。この結果は道具の動作確認であり、研究の結論ではありません。
- 修正後のコードで、4.1 と 4.2 を CLI で実行し直し（分離はキャッシュを使用）、表と同じ値になることを確かめました。

### 4.3 素材の選び方についての確認

- 最初に選んだ5本（奏者01の `Rock3-148-C` など）では、単独ギターの正解率の平均は 0.377 ± 0.215、分離前後の差の平均は +0.050、+0.056、+0.124（伴奏 0、6、12 dB）でした。
- 単独ギターでも正解率が低い録音を調べると、奏者01の `Rock3-148-C` は、ほとんどの区間で根音だけを弾いていました（演奏から推定したコード注釈が `C:(1)/1` など）。指示されたコード（正解）と、実際に弾いた音が一致していませんでした。
- GuitarSet のメジャー／マイナーの伴奏録音120本（全体の長さ、既定の設定）で、`third_played_ratio`（3度の音が少なくとも一度弾かれたコード区間の、時間の割合）と、単独ギターの正解率の関係を確認しました。

| `third_played_ratio` | 録音数 | 正解率の平均 |
| --- | --- | --- |
| 0.9 以上 | 90 | 0.640 |
| 0.5 以上 0.9 未満 | 19 | 0.467 |
| 0.5 未満 | 11 | 0.276 |

- `third_played_ratio` は小数第6位に丸めた値です。`04_Rock1-90-C#_comp` はちょうど 0.5 で「0.5 以上」に入ります（丸めないと計算の誤差で 0.4999… になり、表の値を再現できないことがレビューで分かったため、丸めるように直しました）。修正後のコードで120本を計算し直し、表と同じ値になることを確かめました（環境 A）。

## 9. レビューで見つかった問題と修正

プルリクエストを作った後に、コード・Notebook・文書・仕様への適合をレビューし、次の問題を直しました（それぞれ自動テストまたは実行で確認）。

- 評価：`evaluate` が切り出し位置と解析した範囲を使っていなかった（切り出した結果の正解率が誤る）。`chords.csv` の `source_start_s` から自動で合わせるように直した
- 注釈：音源より長い注釈を、CLI と Notebook では見つけていなかった。音源の長さで確かめ、分離の前に注釈を確かめるように直した。UTF-8 以外の文字コード、列名の空白、空行を含む行番号の扱いも直した
- 判定保留の区間をまとめていた（まとめて平均すると、しきい値を満たすように見える値になる）。区間ごとに残すように直した
- 設定の型（`smoothing_segments = 5.0` など）と範囲の検証、`[analysis]` 表の欠落、`--set` の誤りの表示
- 読み込めない音声ファイル、GuitarSet の録音IDの誤り、通信エラーで、Python の詳しいエラー履歴ではなく原因と対処を表示するように直した
- 分離：不正な設定をモデルの読み込み前に止める、`segment` の上限、メモリ不足のあとにメモリを手放す、GPU のメモリ不足では入力を短くする案内をしない（htdemucs 系では効果がないため）、キャッシュを使ったときも最初の分離時間を記録する
- 比較実験：知らない項目名をエラーにする、同じ音声ファイルの切り出しを同じ元素材とする、伴奏IDの重複、元素材ごとに平均してから集計する、集計ファイルを毎回書き直す、44.1 kHz 以外で混ぜたときの長さのずれ、最初の解析の準備時間を処理時間に含めない、実際に使った設定（既定値を含む）を記録する
